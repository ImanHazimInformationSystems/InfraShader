00.1 RECOMMENDATION ON FINALISING
Baseline a small pilot scope now, subject to team acceptance of this revision.
Do not mark the entire 84-entry roadmap as committed MVP or commercially proven.
No feature can definitely resolve a customer problem until the relevant inputs,
workflow and user acceptance are demonstrated. The proposed changes below are
product judgments informed by research, not proof of willingness to pay.

Primary Studio customer for the next pilot: landscape design-and-build teams
preparing outdoor plans, quantities, estimates and revised client proposals.
Owner-side pilot: project/landscape/facility teams comparing a small set of offers.
A local authority is a possible later customer after policy/deployment discovery;
no named council or government procurement process is validated as a buyer.

CORE VALUE TO TEST
Studio: change a plan -> review updated specifications/quantities/cost -> issue a
consistent revised proposal with visible assumptions and previous version intact.
Owner: receive proposals -> confirm common scope/price basis -> review criteria
and evidence -> record a justified recommendation and authorised decision.
Both workflows must deliver value independently. A contractor can download a
proposal without a buyer account; an owner can compare authorised external files.

00.4 CORE STUDIO BOUNDARY
- Brief/site facts with unknowns and client-confirmation record (L01/L03/K01).
- Existing map, baseline, measurements, basic objects, A/B and supported shade.
- Minimum precise editing: snapping where supported, numeric dimensions, duplicate,
  layers and dependable undo; batch/groups/complex split-merge can follow (L04).
- Calibrated admitted image/single PDF-page reference with manual confirmation;
  no CAD extraction or automatic survey conversion (L05/K05).
- Small user-curated plant/material list; plant code/name/nursery size/unit/spacing,
  manual or explicit geometric count method and automatic schedule (L09/L10/L13).
- Simple material/labour/equipment/transport/overhead cost build-up, rate source/
  expiry, charge-inclusion checks and markup/margin explanations (L14-L16/K04).
- Change-impact/revision ledger and selected-option comparison, preserving issued
  records (L12/L26/K02/K03).
- Plan sheet + schedule + quote/proposal with scope/exclusions, price basis,
  retained files and deliberate issue (L23/L24).
- Required security/recovery/export and limited maintenance assumptions checklist.
No requirement to add terrain sculpting, custom GLB, engineering hydraulics,
advanced building imports, full CRM or production scheduling to finish this slice.

00.5 CORE OWNER BOUNDARY
- One project with owner brief/baseline, requirements and an approved criteria version.
- Intake native disclosed packages by authorised upload OR external PDF/XLSX with
  manual field confirmation. Interactive cross-tenant invitations/submission portal
  can follow; do not require every supplier to register before the owner gets value.
- Small common BOQ/scope table: original offer, confirmed mapping, unit/tax/inclusion
  differences, missing items and comparison-only adjustments (O05-O07/K06).
- View submitted maps when present; document-only fallback is valid (O08).
- Transparent weighted scorecard with source/rationale, missing-data rules and
  simple reviewer assignment; no autonomous AI scoring/selection (O09/O10/O12/O14).
- Basic notes/clarification register, manual recorded client response, one simple
  reviewer-to-authorised-approver transition and retained decision pack (O15-O17).
- Small dashboard of counts/budget/completion backed by the same confirmed records.
No portfolio optimiser, sealed tender, complex approval builder or ERP/SSO migration
is required for this first review slice.

00.6 COMMON TRANSACTION RULES
A changed design does not mutate an issued proposal or accepted baseline.
An estimated map measurement is not silently promoted to a verified dimension.
A missing price/item is never silently converted to zero or treated as included.
Plant crown/3D size does not establish procurement size or actual shade performance.
A revision invalidates dependent draft outputs; completed records remain retained.
The owner sees submitted selling scope/price, not contractor internal profit.
An AI finding cannot edit official quantities/prices/criteria, approve, issue or send.
Each source field links to its originating record/version or document page/row.

00.7 SIX FOCUSED REQUIREMENT REFINEMENTS - K01-K06
These strengthen existing features; they do not create six new standalone modules.
All added behaviours below are PLANNED / NOT VERIFIED IN CODE.

K01 - AGREED BRIEF, SCOPE AND ASSUMPTIONS CHECKPOINT
Problems: P01/P03. Extends L01/L03/L24, O02 and S10.
- Record deliverables, inclusions/exclusions, budget range, intended use, unresolved
  questions and who supplied each fact. Separate known/estimated/unknown.
- Contractor reviews brief with client; record confirmation date, person, method
  and attached evidence. Permit explicit 'not confirmed' status with issue policy.
- Accepted brief version is referenced by proposals; subsequent changes create a
  new draft version. This is acknowledgement evidence, not a digital-signature service.
UI: Brief readiness checklist and versioned confirmation panel.
Resources: X01/X04/X05; existing forms/database/files, no new paid service.
Acceptance: outstanding assumptions remain visible; cannot imply client acceptance
from an internal draft checkbox or modify an earlier confirmation retrospectively.

K02 - DEPENDENCY-AWARE CHANGE IMPACT AND CONSISTENCY CHECK
Problems: P02/P04. Extends L04/L09-L13/L24, D06 and S06.
- Track object revision -> plant/material schedule -> quantity -> rate selection ->
  estimate -> proposal draft/analysis. Record which input invalidated a result.
- Provide a simple impact list: affected items, quantity/cost differences and
  work that needs human review; detect orphaned estimate lines/unpriced scope.
- Begin with reliable project/scenario revision checks. Fine-grained dependency
  optimisation comes only after correctness; do not promise a spreadsheet engine.
UI: 'Changed since last issue' drawer with links and recompute/review actions.
Resources: X01-X05; transaction/revision business logic is custom InfraShader code.
Acceptance: edit, delete, undo, duplicate and rate replacement produce correct draft
results or explicit stale states; issued artifacts/files stay unchanged.

K03 - CHANGE REQUEST AND COMMERCIAL IMPACT RECORD
Problems: P01/P02/P04. Extends L12/L26, O15 and S03/S10.
- Capture requester/date/reason, original scope and proposed addition/removal.
- Compare quantity/price/time assumptions with the last issued reference version.
- Record prepared/reviewed/sent/acknowledged/rejected states with evidence; make
  revised proposal issuance explicit. Acknowledgement is not automatically payment.
- Support standalone contractor record/download before a two-sided portal exists.
UI: Change register and concise revision/change summary appendix.
Resources: X01/X04/X05; no contract-signature or payment integration required.
Acceptance: internal draft cannot masquerade as client-approved change; historical
price snapshots reproduce exactly; scope updates do not silently amend a contract.

K04 - PRICE VALIDITY AND ESTIMATE COMPLETENESS GATE
Problems: P04/P05. Extends L13-L16/L24, O07/O13.
- Rate source/date/expiry and included labour/equipment/transport semantics.
- Flag stale rates, missing units/quantities/rates, incompatible dimensions,
  duplicate inclusive charges, unpriced items and optional/provisional lines.
- Display priced-scope completeness by count and value only where meaningful;
  unknown amounts prevent a misleading '100% total cost coverage' claim.
- Show proposal validity/assumptions; overrides require reason and authorised review.
UI: Estimate readiness panel and proposal warning summary.
Resources: X04/X05/X08; deterministic checks, not LLM price invention.
Acceptance: missing line prices cannot pass silently as zero; output never exposes
internal margin; expired rate is flagged rather than automatically replaced.

K05 - MEASUREMENT SOURCE AND SITE-VERIFICATION QUEUE
Problems: P02/P03/P08. Extends L03-L05/L13 and F02/F04/F05.
- Label map-derived, traced, measured or supplied dimensions and confidence category.
- Connect evidence/reference plan, known calibration dimension and measurement date.
- List critical facts requiring site check; assign responsible person and resolution.
- Record measured override and effect on quantity without altering original source.
UI: Source badges and 'Verify on site' list beside quantity/map inspector.
Resources: X02-X04/X06; existing evidence and calibrated overlay plus custom logic.
Acceptance: unknown height stays unknown; reference replacement flags traced records
for review; no claim of survey accuracy from unverified basemap imagery.

K06 - COMPARISON READINESS AND REVIEW COVERAGE CHECK
Problems: P05/P06/P07. Extends O06-O14/O17/O18.
- Confirm proposal versions, common scope/site/time basis, units/currency/tax,
  exclusions, optional work, maintenance basis and source evidence before comparison.
- Show comparable/needs clarification/document-only/unpriced/ineligible separately.
- Report missing required criteria scores and reasons. Do not redistribute weights,
  guess scope or approve on incomplete data without a recorded permitted exception.
- Add source-linked unresolved questions and review-completeness summary to report.
UI: Readiness banner and unresolved-items panel in comparison/decision pack.
Resources: X04-X08/X10; deterministic validation; A03 suggestions optional later.
Acceptance: cheaper incomplete offer cannot silently become 'best value'; every
comparison adjustment has a reason/source and differs visibly from quoted total.

NEW ACCOUNT / ONBOARDING

RETURNING LOGIN

- Revalidate stored workspace/organisation preferences; they are convenience state,

STAFF ROLES AND CAPABILITIES

Project purpose is separate from active organisation/workspace/member capability.
Creating a contractor-purpose project must not grant internal pricing to a buyer.
An owner can inspect a submitted map without acquiring contractor design-edit rights.

01. PRODUCT DIRECTION, SCOPE AND STATUS DEFINITIONS
==============================================================================

InfraShader connects outdoor landscape design, quantities and proposals with
structured client-side comparison and approval. Two interfaces use a common
platform; each organisation retains ownership of its own private information.

A. LANDSCAPER / CONTRACTOR: a spatial design studio for landscape designers,
landscape design-and-build firms and outdoor contractors, including small teams.
Primary work: understand site -> design -> measure -> estimate -> prepare an
option/proposal -> submit an approved package -> answer clarification requests.
Professional does not mean every CAD/engineering discipline is included.

B. LARGE ORGANISATION: an owner-side project and proposal review workspace for
property developers, campus/facility owners, corporate estates and local-authority
teams. Primary work: define project/criteria -> collect proposals -> verify and
normalise -> compare -> evaluate -> approve or request changes -> retain record.
A Perak local-authority team is an illustrative prospect, not an identified
customer. Confirm the actual council, department, needs and authority in a pilot.

An organisation can have BOTH capabilities. Interface choice controls navigation;
server-verified organisation membership, project grants and capabilities control
access. A contractor cannot become a buyer/reviewer by changing a profile label.
Large-organisation users receive a review viewer; full editing needs a separate
capability. Existing developer concept review is not a completed review portal.

resource ownership/grants on every request, background job and file retrieval.

Role                  Normal capabilities                   Restricted by default
Designer              Own layouts, evidence, analyses        Profit, other bidders
Estimator             Own BOQ/rates/internal build-ups       Buyer-only deliberation
Contractor submitter  Approve/publish own disclosed package  Other contractors' work
Buyer coordinator     Briefs, invitations, receipt workflow  Contractor private costs
Technical evaluator   Assigned technical evidence/scores     Restricted financial data
Financial evaluator   Permitted submitted price/comparison   Contractor internal profit
Committee chair       Moderation and decision recommendation Silent score rewriting
Approver              Approved pack; return/approve/reject    Editing submitted bids
Auditor               Granted read-only decisions/events     Unrelated projects/tenants
Org administrator     Membership/policy administration       Automatic access to bids

An administrator's membership-management ability does not imply evaluation or
opening privileges. Explicitly define privileged operator/storage access; an
application access matrix alone cannot protect data from all infrastructure admins.

INFORMATION OWNERSHIP
Contractor private: drafts, alternatives not submitted, internal costs/profit,
supplier-private quotations, design notes and private AI retrieval corpus.
Disclosed package: selected selling price/scope, approved visuals/BOQ, declared
assumptions, selected evidence, package ID/version and agreed terms fields.
Buyer private: rubric drafts, evaluator notes/scores, moderation, internal budget,
AI findings and approval records. Disclose outcomes only through approved actions.
Shared: published brief/addenda, permitted questions/answers and receipt/status.

Required tests: supplier A versus supplier B versus buyer; wrong project grant;
revoked member; stale signed URL; background job/cached embedding leakage;
download/export payload; artificial role/workspace switch; support/admin scope.
Start read/write permissions with denial and add named grants. Avoid giving a
recipient live read access to the full contractor project as a sharing shortcut.

08. DATA CONTRACTS, SCORING RULES AND EXAMPLE EVALUATION
==============================================================================

PROPOSED ENTITIES (DESIGN, NOT EXISTING DATABASE CLAIMS)
Reuse organisations, memberships, projects, stakeholders, geometry, scenarios,
rates, evidence, calculation artifacts, reviews and issued snapshots where viable.
Add owner_projects/packages, published_briefs/addenda, invitations, submissions,
submission_versions/files, disclosure_manifests and recipient_grants.
Add requirements, canonical_boq_items, reviewed_line_mappings, normalisations,
criteria_sets/rubrics, evaluator_assignments, conflict_declarations, scores,
moderation_records, approval_steps/actions and decision_snapshots.
Add discussion_threads/messages, tasks/notifications, retained_file_versions,
job_runs, extraction_fields/source_anchors, retrieval_chunks and ai_findings.
Add optional plant/material libraries, maintenance_plans and handover_assets
in their respective delivery stages, not all in the next migration.

Cross-organisation references must represent an explicit exchange. Do not replace
the contractor's tenant_id with the buyer tenant or share a mutable design row.

SUBMISSION SNAPSHOT MINIMUM
schema_version, submission_id/revision, sender_org, recipient_org/project,
brief/baseline version, received_at and deadline rules; declared MYR price/unit/
tax/inclusions basis; approved BOQ and option geometry if supplied; analysis
method/input revision/date/time/target/limitations; evidence/file manifest/hashes;
permitted narrative; author/approver and disclosure scope. Preserve original files.
No internal cost/profit columns. Missing required information is an explicit
state, not an empty string that later becomes zero.

SOURCE ANCHOR MINIMUM
submission_version_id, file_version/hash, page, section, table/row/cell or
bounding box; original text/value/unit; parser/version; reviewer correction,
actor/time and certainty category. A model statement must link to actual source
anchors. Never claim an LLM's self-reported confidence is a calibrated probability.

CANONICAL COMPARISON
Preserve original quotation and map to common units/scope through reviewed rules.
Keep quantity, rate, amount, currency, tax basis, optional/excluded/missing status,
allowances and price validity separately. Never treat a missing line as zero cost.
Comparisons for different site areas, dates or use-time targets must disclose the
difference or block a misleading headline. Maintain technical and financial
source restrictions when creating dashboard aggregates and AI contexts.

WEIGHTED SCORING (CUSTOM PYTHON BUSINESS LOGIC, N08)
- Eligibility gates are separate from weighted preference scores.
- Weights must be non-negative and total 100%; approve and freeze a rubric version.
- A manually assessed criterion has a stated scale/rubric, e.g. 0-5; map to 0-100
  only with a declared conversion. Higher-is-better and lower-is-better numerical
  criteria use approved thresholds/direction, not a generic hidden normaliser.
- For reviewer-confirmed criteria, weighted total = SUM(weight_fraction * score).
- Missing required evidence blocks finalisation or follows a predeclared missing-
  data rule. Never silently redistribute weights or reward missing information.
- Tie handling, reviewer aggregation, moderation and disqualification are stated
  policy. Store formula version, eligible input set and the complete calculation.
- Official rubric changes require authorisation/re-evaluation. What-if weights
  produce a separate scenario and cannot silently change official ranking.
- A price formula such as 100 * lowest_eligible_price / bidder_price is merely
  an optional policy example. Validate positive comparable prices and sensitivity
  to the eligible set; adopt only if the owner approves. No Malaysian mandatory
  formula is asserted here.

ILLUSTRATIVE CRITERIA ONLY - NOT ACTUAL PROCUREMENT RULES
Design/function 25%; comparable price 25%; maintenance 20%; evidence-based outdoor
outcomes 20%; programme 10%. Owner must approve criteria and rationale beforehand.
Shade is a supported indicator where validated, not the entire sustainability score.

Example confirmed scores (0-100) for three fictional proposals:
Proposal     Design   Price   Maintenance   Outcomes   Programme   Total
A            80       90      60            70         80          76.5
B            90       70      85            85         75          81.5
C            70       95      50            60         90          72.25
A = 0.25*80 + 0.25*90 + 0.20*60 + 0.20*70 + 0.10*80 = 76.5.
B has the highest weighted example score; this is not an automatic award.
Show underlying evidence and eligibility, uncertainty and sensitivity. These
scores are illustrative inputs, not AI assessments or evidence of product value.

WORKFLOW STATES
Proposal: private draft -> contractor-approved -> submitted -> received ->
under clarification -> revised/superseded/withdrawn -> considered/closed.
Review: intake -> extraction review -> eligibility -> individual evaluations ->
moderation -> recommendation -> approval/return/rejection -> decision record.
Define allowed transitions, actor capabilities, revision preconditions and reason
fields. Reopening an evaluation creates a new auditable version, not silent edits.

searchable tables, clear progress, source links, readable empty/error states.

WORKFLOW A - SMALL LANDSCAPE CONTRACTOR
Sign in -> select own organisation -> new client/project -> explore/select site ->
brief/evidence/constraints -> draw/place objects -> compare A/B -> check supported
shade and quantities -> rate/cost review -> price -> preview approved disclosure ->
retain issue PDF -> download/share manually OR submit to invited buyer package ->
receipt -> clarification -> deliberate revised submission.
Advanced terrain/GLB/planting tools insert into design only after their stage ships.

WORKFLOW B - OWNER / LOCAL AUTHORITY / LARGE DEVELOPER
Select organisation/project -> create owner brief/baseline -> define requirements,
common response template and criteria -> approve/lock -> invite contractors ->
receive native packages or authorised external PDF/XLSX -> inspect extraction ->
confirm mappings/eligibility -> compare scope/cost/maps -> individual evaluation ->
moderate -> review AI findings if enabled -> approve recommendation/return ->
retain decision pack -> controlled notification/export -> later handover tracking.

WORKFLOW C - PROPOSAL FROM A FIRM WITHOUT INFRASHADER
Buyer records an external receipt -> uploads authorised PDF/XLSX -> validates/
extracts -> manually confirms fields -> compares as document-only unless licensed
geometry is explicitly supplied. A supplier account is not mandatory for an owner
to evaluate an authorised external proposal. Do not invent a 3D model from a PDF.

WORKFLOW D - ONE COMPANY BOTH DESIGNS AND REVIEWS
Separate organisations/projects or explicit grants; switch workspace through the
same login. Evaluation conflicts and recipient disclosures remain enforced. A
workspace toggle never grants access to competitor private data or internal scores.

WORKFLOW E - AI UNAVAILABLE
Manual forms, evidence reader, deterministic normalisation/scoring, comparisons,
approvals and exports remain usable. Queue/error status explains unavailable
assistance; reviewers can enter and confirm information directly.
